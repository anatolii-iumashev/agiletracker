# Spec: REST API v1 on Lomkit and Scramble

## What was done

The public REST API v1 lives under `/api/v1` and is protected by Sanctum tokens. Four Lomkit
resources (`App\Rest\Resources\{Item,User,Label,Comment}Resource`) are declared declaratively and
expose the same set of operations: `details`, `search`, `mutate`, plus `destroy` for
items/labels/comments. Items additionally have an `assign` action. There are no traditional
list/show/store/update routes: the list and a single record are fetched through `POST /search`
(filter `id = ...`).

| Resource | URI | Abilities | Specifics |
|---|---|---|---|
| Items | `/api/v1/items` | `items:read`, `items:write` | `is_epic`, virtual `type` from `meta.type`, labels attach/detach/sync, 409 on active children, `assign` action |
| Users | `/api/v1/users` | `users:read`, `users:write` | write-only password, create/update `admin` only, roles are not exposed, no destroy |
| Labels | `/api/v1/labels` | `labels:read`, `labels:write` | delete clears `item_label` only, `items` relation is read-only |
| Comments | `/api/v1/comments` | `comments:read`, `comments:write` | author = current user, author/admin rules, perimeter over a live Item |

The shared rules live in `App\Rest\Resources\Resource`: `Contains` search, limits
`[15,25,50,100]`, `id DESC` ordering, `search.trashed` rejected with 422. Authorization has two
layers: the token ability (a Gate in `AppServiceProvider`) plus the model policy. Rate limit — 60
requests per minute per user ID or IP. `php artisan rest:check` passes: 17 routes authenticated, 4
policies, the action checks every row.

Documentation is generated by Scramble from the same declarations: `/docs/api` (UI) and
`/docs/api.json`, the `tests/api.json` snapshot is committed. The Item delete 409 response and the
bearer scheme are added by OpenAPI transformers.

## Key decisions

- **A single source of the contract.** Fields, relations, rules, filters and actions are declared
  only in the REST resource; API Resources, Form Requests and Scribe are not used.
- **`type` is a virtual field over `meta.type`.** Read via `resolveUsing`, written via `fillUsing`
  (the remaining `meta` keys are preserved), filtered via `meta->type`, allowed values
  `task|bug|feature`. Older records without a type are read as `null`.
- **`is_epic` is a separate flag.** The new `items.is_epic` (boolean, default false, index
  `(is_epic, id)`) does not change `type`; the hybrid `type=task + is_epic=true` is a valid
  container task.
- **The hierarchy changes only through `parent_id`.** The `parent`/`children` relations are
  declared read-only (`onlyOperations()`), so the tree can be written only by changing `parent_id`.
  A cycle (the item itself or a descendant) returns 422 and rolls back the whole mutation.
- **Label membership goes through Item only.** `ItemResource.labels` accepts `attach`/`detach`/`sync`;
  `LabelResource.items` is read-only so that there are no two competing write APIs.
- **Destroy with a domain constraint.** An Item with active children responds 409 without changes;
  every other delete is soft and transactional.
- **Comment perimeter.** `CommentResource::perimeterQuery()` performs `whereHas('item')`: comments
  of a deleted Item stay in the database but are not visible, mutable or deletable through the API.
- **User safety.** `password` is declared `writeOnly`, so it is never returned, filtered or sorted;
  `remember_token`, `email_verified_at` and roles are not declared at all. The unique email rule on
  update ignores the current record via `Contextual::rule()`.
- **Snapshot instead of a hand-written collection.** `tests/api.json` is the OpenAPI 3.1 export;
  the `ApiDocumentationTest` test re-exports the document and fails on any difference.

## Deviations from the RFC

- **`includeLimit` = 15, not 10.** The package requires `$includeLimit` to be part of `limits()`;
  with limits `[15,25,50,100]` the default value of 10 throws `InvalidResourceException`.
- **`password` is marked with the `Write-only.` description rather than the OpenAPI `writeOnly`
  flag.** Scramble 0.13 does not support `writeOnly` on schemas; the field is still absent from the
  User write schema and appears only in `UserCreate`/`UserUpdate`.
- **`CommentPolicy::create` allows any authenticated user.** The existence and non-deleted state of
  `item_id` is checked by the field rule, so the client receives 422 (as in the RFC) rather than a
  403 from the policy. The `view/update/delete` policy restricts the author and `admin`.
- **Access to `/docs/api` is limited to `local`/`testing`.** The public access policy for the UI
  remains an open question in the RFC; in production the page stays closed until a separate
  decision.
- **There is no CI configuration in the repository.** The role of "CI fails on a diff" is played by
  the `the committed snapshot is up to date` test in `ApiDocumentationTest`, which runs together
  with `php artisan test` in any pipeline.
- **`SmokeTest` hits `/i`, not `/items`.** The Filament Item resource has the slug `i`; the test was
  aligned with the actual route (this was a mismatch that predates the RFC).

## Known limitations / next steps

- There is no token issuance through the API: tokens are created manually or by commands
  (`createToken`).
- There is no user deletion, role or permission assignment through the API — a separate lifecycle
  RFC.
- There is no restore/force delete and no reading trashed records; `search.trashed` intentionally
  returns 422.
- There are no metrics, queues, batched actions, webhooks, OAuth2 or public SDKs.
- Search is `Contains` over SQL; as data grows, `FullText`/Scout and indexes will be needed.
- The access policy for `/docs/api` in production is not defined.
- The 60/min rate limit is shared by all four resources; named limiters can be added at the
  action/resource level when needed.
